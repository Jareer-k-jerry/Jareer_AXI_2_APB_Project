1. Complete UVM Testbench Hierarchy & Architecture Diagram

Verification ka maqsad yeh hota hai ke hum DUT (Design Under Test) ko ek aisi environment mein band karein jahan hum har input ko control kar sakein aur har output ko cycle-accurate verify kar sakein.

Hamara AXI2APB Testbench standard UVM 1.2 structure ko follow karta hai. Is mein do distinct agents hain: ek Active AXI Master Agent (jo stimulus generate karta hai) aur ek Active Reactive APB Slave Agent (jo memory/peripheral ban kar Bridge ki requests ka response deta hai).

2. Agent 1: AXI Master Agent (Item, Sequencer, Driver, Monitor)

AXI Master Agent ka role yeh hai ke woh AXI transactions ko simulate kar ke Bridge ke inputs par drive kare aur pin-level bus activity ko monitor kare.

1. Transaction Item: axi_master_item.sv

Yeh class data aur control parameters ko encapsulate karti hai:

  • rand bit write: 1 for write transaction, 0 for read.
  • rand bit [31:0] addr: 32-bit transaction address (must satisfy addr[1:0] == 2'b00 for word alignment).
  • rand bit [31:0] data: 32-bit payload data.
  • rand bit [15:0] id: AXI Transaction ID (AWID / ARID).
  • rand bit [9:0] user: AXI sideband metadata (AWUSER / ARUSER).
  • rand int unsigned bready_delay / rready_delay: Ready handshake insertion delay.

2. Sequences: Stimulus Generation

Sequences driver ko items feed karti hain:

  • axi_single_write_seq: Specific address par targeted write generate karta hai.
  • axi_single_read_seq: Specific address se read generate karta hai.
  • axi_constrained_random_seq: Configurable num_trans ke sath continuous random read/write transactions generate karta hai.

3. Driver: axi_master_driver.sv

Driver virtual interface (axi4_if) ke clocking block par AXI pin-level handshake drive karta hai: 

// Write Channel Execution:
vif.master_cb.awaddr  <= tr.addr;
vif.master_cb.awvalid <= 1'b1;
vif.master_cb.wdata   <= tr.data;
vif.master_cb.wvalid  <= 1'b1;
// Wait for AWREADY and WREADY handshakes...
wait (vif.master_cb.awready && vif.master_cb.wready);
// Wait for BVALID from Bridge and assert BREADY...

4. Monitor: axi_master_monitor.sv

Monitor passively pins ko observe karta hai. Jab bhi AXI handshake mukammal hota hai (e.g. Write response par BVALID && BREADY ya Read data par RVALID && RREADY), monitor item create karta hai aur apne analysis_port.write(tr) ke zariye Scoreboard aur Coverage ko bhej deta hai.

3. Agent 2: APB Slave Agent (The Reactive Slave Concept & Wait States)

Core Verification Concept: Reactive Slave Agent Kya Hota Hai? Master Agent hamesha Proactive hota hai (woh apni marzi se jab chahe transfer start karta hai). Lekin Slave Agent hamesha Reactive hota hai! Slave tab tak koi response nahi de sakta jab tak Bridge APB par PSEL && PENABLE assert na kare!

Reactive APB Driver Kaise Kaam Karta Hai?

APB Driver (apb_slave_driver.sv) bus par baith kar intezar karta hai. Jaise hi Bridge APB transfer start karta hai, Driver sequencer se response item mangta hai:

  1. Wait State Generation: Response item mein wait_cycles ki value hoti hai (e.g. 0 to 4 cycles). Agar wait_cycles > 0 hon, to Driver PREADY <= 1'b0 rakhta hai utnay clock cycles tak!
  2. Completion Phase: Wait cycles mukammal hone par Driver PREADY <= 1'b1 assert karta hai aur agar Read operation ho to PRDATA <= tr.read_data drive karta hai.
  3. Transfer complete hote hi Driver wapis IDLE ho jata hai.

APB Monitor: Cycle-Accurate Wait State Measurement

[apb_slave_monitor.sv](file:///d:/Summer_2026/IC_DESIGN_preperation/NECOP/Design_Verification/JAREER_project/Jareer_AXI2APB_project/tb/apb_slave_agent/apb_slave_monitor.sv) mein hum ne exact wait cycle counting implement ki hai: 

// Wait until transfer starts (PSEL && PENABLE)
do begin
  @(vif.monitor_cb);
end while (!(vif.monitor_cb.psel && vif.monitor_cb.penable));

// Count every cycle while PREADY remains low!
while (!vif.monitor_cb.pready) begin
  measured_waits++;
  @(vif.monitor_cb);
end

tr.wait_cycles = measured_waits; // Exact measured wait states published to coverage!

4. Transaction Scoreboard Architecture & Matching Queues

Scoreboard (axi2apb_scoreboard.sv) verification environment ka judge hota hai. Iska kaam AXI side se aane wali transaction ko APB side par aane wali transaction ke sath compare karna hai.

Scoreboard Data Flow & Queues

Exact Matching Rules

Operation AXI Observed Field APB Observed Field Check Performed by Scoreboard
Write Check axi_item.addr, axi_item.data apb_item.addr, apb_item.write_data assert(axi_item.addr == apb_item.addr)
assert(axi_item.data == apb_item.write_data)
assert(apb_item.write == 1'b1)
Read Check axi_item.addr, axi_item.data (RDATA) apb_item.addr, apb_item.read_data (PRDATA) assert(axi_item.addr == apb_item.addr)
assert(axi_item.data == apb_item.read_data)
assert(apb_item.write == 1'b0)
The check_expected_transactions Knob: Jab hum Reset ya Smoke test chalatay hain to bus par zero transactions hoti hain. Agar scoreboard end of test par matches == 0 par error throw kare to smoke test fail ho jayega! Is liye scoreboard mein hum ne ek configuration knob diya hai: uvm_config_db#(bit)::set(this, "env.scoreboard", "check_expected_transactions", 1'b0); Yeh knob smoke test ko clean pass hone deta hai jabke normal tests mein transaction count strictly verify hota hai.

5. Unified Functional Coverage Collector & Cross Coverage

Coverage engineer ko yeh batati hai ke kya hum ne test plan ke tamam verification scenarios ko cover kar liya hai ya nahi. Hamare collector (axi2apb_functional_coverage.sv) ke andar key coverpoints hain:

Coverpoint Name Monitored Variable Bins Defined Maqsad (Verification Goal)
cp_axi_addr axi_item.addr low_range [0:16'h0FFF]
mid_range [16'h1000:16'h7FFF]
high_range [16'h8000:16'hFFFF] 		Verify karna ke bridge memory map ke har region ko access kar sakta hai.
cp_axi_write axi_item.write bins write = {1}, bins read = {0} Read aur Write dono directions ko cover karna.
cp_apb_wait_cycles apb_item.wait_cycles zero_wait = {0}
short_wait = {[1:3]}
long_wait = {[4:8]}
high_wait = {[9:15]} 		Verify karna ke Bridge fast slaves (0 wait) aur slow stalled slaves (1-15 waits) dono ke sath sahi chal raha hai.
cp_user axi_item.user[9:0] zeros, ones, rand_bins User sideband signal propagation check karna.
cross_addr_op cross cp_axi_addr, cp_axi_write Har address range par read aur write dono ka cross Yeh ensure karna ke har address range par sirf read nahi balki write bhi test hua hai!
RTL Limitation Handling in Coverage (ignore_bins): Chunkay DUT RTL mein BRESP aur RRESP hamesha 2'b00 (OKAY) hardcoded hain, is liye EXOKAY, SLVERR, aur DECERR bins ko ignore_bins mein rakha gaya hai. Is se coverage calculation bilkul accurate rehti hai aur artificial 50% penalty nahi lagti.

6. All 5 Phase-5 Directed Testcases Explained Line-by-Line

Phase 5 mein 5 fundamental directed tests hain jo basic functionality ko step-by-step verify kartay hain:

Test 1: axi2apb_smoke_test DIRECTED

Goal: Reset assertion, reset release recovery, aur post-reset IDLE stability check karna.

Working: Test wait karta hai ke ARESETn == 0 ho aur phir ARESETn == 1 release ho jaye. Uske baad 20 clock cycles tak observe karta hai ke Bridge IDLE state mein koi spurious PENABLE, BVALID, ya RVALID assert to nahi kar raha. Agar koi spurious signal aaye to test fail hota hai.

Test 2: axi2apb_single_write_test DIRECTED

Goal: Clean single AXI Write operation from start to finish.

Working: Master address 32'h0000_1000 par data 32'hDEAD_BEEF bhejta hai. APB slave immediate response (wait_cycles = 0) deta hai. Scoreboard verify karta hai ke APB par same address aur data deliver hua aur AXI par BRESP == OKAY return hua (matches == 1, errors == 0).

Test 3: axi2apb_single_read_test DIRECTED

Goal: Clean single AXI Read operation from start to finish.

Working: Master address 32'h0000_2000 par read request bhejta hai. Reactive APB slave PRDATA = 32'hFEED_FACE drive karta hai. Scoreboard verify karta hai ke master ko wahi data wapis mila.

Test 4: axi2apb_wait_state_test DIRECTED

Goal: APB slave wait states (stalled PREADY) ke sath bridge ka behavior check karna.

Working: Phase 1 mein Write transaction ke sath 3 wait cycles inject kiye jatay hain. Phase 2 mein Read transaction ke sath 4 wait cycles inject kiye jatay hain. APB monitor actual cycles count karta hai aur scoreboard verify karta hai ke stalling ke bawajood data corrupt nahi hua.

Test 5: axi2apb_simultaneous_rw_test DIRECTED

Goal: Read-Priority Arbitration verify karna jab Read aur Write requests bilkul aik hi clock edge par aayen.

Working: Test pin-level clocking block ke zariye ARVALID <= 1 aur AWVALID <= 1 ko exact same clock cycle par assert karta hai. DUT read priority ki wajah se pehle Read complete karta hai aur baad mein Write. Scoreboard total 2 matches confirm karta hai.

7. All 6 Phase-6 Randomized & Constrained-Random Testcases

Phase 6 mein tamam scenarios ko randomized banaya gaya hai aur ek comprehensive multi-transfer constrained-random test banaya gaya hai:

1. axi2apb_random_smoke_test RANDOMIZED SCENARIO

Randomization: idle_cycles inside [20:50] randomized hotay hain. Har run mein different duration tak IDLE stability check hoti hai.

2. axi2apb_random_single_write_test RANDOMIZED SCENARIO

Randomization: Address (legal 4-byte aligned), 32-bit data payload, 16-bit Transaction ID, aur 10-bit USER field poori tarah randomize hotay hain.

3. axi2apb_random_single_read_test RANDOMIZED SCENARIO

Randomization: Random read address, random ID, random USER, aur APB peripheral memory data (rand_rdata) bhi pre-randomized hota hai.

4. axi2apb_random_wait_state_test RANDOMIZED SCENARIO

Randomization: Write aur Read dono operations ke liye wait states strictly non-zero (inside [1:4]) randomize hoti hain. Yeh guaranteed wait-state coverage deta hai.

5. axi2apb_random_simultaneous_rw_test RANDOMIZED SCENARIO

Randomization: Dono read aur write ke addresses, data, aur IDs randomized hotay hain aur unhein exact same clock edge par simultaneously present kiya jata hai.

6. axi2apb_constrained_random_test MULTI-TRANSFER STRESS TEST

The Mega Coverage Booster Test:

Yeh test ek continuous stream of randomized AXI read/write transfers run karta hai jahan APB slave har transfer par dynamic randomized wait states (0 se 4 cycles) inject karta hai.

Dynamic CLI Parameter (+NUM_TRANS): Aap CLI se runtime par control kar saktay hain ke kitni transactions chalani hain:
make run TEST=axi2apb_constrained_random_test +NUM_TRANS=50
Default value = 20 transactions. Scoreboard dynamically total transactions ko track aur verify karta hai.

8. Synopsys VCS Simulation & Coverage Merging Workflow

Hamare [sim/Makefile](file:///d:/Summer_2026/IC_DESIGN_preperation/NECOP/Design_Verification/JAREER_project/Jareer_AXI2APB_project/sim/Makefile) mein poori verification suite ko automate kiya gaya hai: 

# 1. Koi bhi specific directed ya random test run karne ke liye:
make run TEST=axi2apb_single_write_test
make run TEST=axi2apb_random_wait_state_test
make run TEST=axi2apb_constrained_random_test

# 2. Custom transaction count ke sath multi-transfer test chalana:
make run TEST=axi2apb_constrained_random_test +NUM_TRANS=100

# 3. Tamam Directed Tests ki regression chalana aur coverage merge karna:
make regression_directed

# 4. Tamam Randomized Tests ki regression chalana aur coverage merge karna:
make regression_random

# 5. Full Suite (Directed + Random) ek sath run karna:
make regression_all

# 6. Merged Functional Coverage GUI Report open karna:
make func_covg_gui
VCS Unified Coverage DB Mechanism: Har test run ke waqt Makefile -cm_name $(TEST) use karta hai aur database ko ./out/build_$(TEST)/simv.vdb mein save karta hai. Jab make coverage chalta hai, to urg -dir ./out/build_*/*.vdb tamam databases ko merge karta hai. URG report ke andar "Tests" tab mein har test ka apna name alag alag identify hota hai!

9. Top 10 UVM & Verification Technical Interview Questions

Q1: Aapke UVM Environment mein do agents kyun hain aur unka active/passive mode kya hai?
Jawab (Roman Urdu): Environment mein do agents is liye hain kyunke Bridge ke do alag interfaces hain: ek AXI4 Master interface aur ek APB Slave interface.
Dono agents ACTIVE mode mein hain:
  • AXI Master Agent: Active hai kyunke yeh AXI transfers generate aur drive karta hai.
  • APB Slave Agent: Yeh bhi Active hai lekin Reactive role play karta hai; yeh memory model ban kar PREADY aur PRDATA drive karta hai.
Q2: APB Slave Agent ko reactive kaisay banaya gaya hai? Driver sequencer se item kab leta hai?
Jawab (Roman Urdu): APB slave proactive nahi ho sakta kyunke APB bus par slave tab tak kuch nahi kar sakta jab tak master request na kare. Is liye Driver loop mein @(vif.monitor_cb) par wait karta hai jab tak PSEL && PENABLE active na ho jayein. Jaise hi transfer detect hota hai, Driver seq_item_port.get_next_item(req) call karta hai, wait states inject karta hai, aur transfer complete hone par item_done() call karta hai.
Q3: Scoreboard mein In-order matching kaise kaam karti hai?
Jawab (Roman Urdu): Chunkay APB bus un-pipelined aur in-order hai, is liye Bridge par jis sequence mein AXI requests aati hain, usi sequence mein APB par execute hoti hain. Scoreboard do internal FIFOs maintain karta hai: axi_pending_q[$] aur apb_pending_q[$]. Jab AXI aur APB dono se matching transactions aa jati hain, scoreboard unke addresses aur data payloads ko pop kar ke compare karta hai. Agar match ho to matches++, warna errors++ increment hota hai.
Q4: Simultaneous Read/Write test mein race condition se bachne ke liye aap ne kya kiya?
Jawab (Roman Urdu): Agar hum do sequences (Read aur Write) ko same AXI sequencer par fork...join se start karein, to sequencer arbitration ek sequence ko pehle grant karega aur driver pehle usay mukammal karega. Is tarah DUT ke pins par dono requests kabhi simultaneous nahi pahunchein gi!
Is race condition ko khatam karne ke liye hum ne pin-level direct clocking block driving use ki: axi_vif.master_cb.arvalid <= 1 aur axi_vif.master_cb.awvalid <= 1 ko exact same clock edge par assert kiya, jis se DUT ki hardware arbitration (Read Priority) 100% guarantee ke sath verify hui.
Q5: APB Monitor actual wait cycles kaisay measure karta hai?
Jawab (Roman Urdu): APB Monitor jab dekhta hai ke psel && penable assert ho gaye hain, to woh clock edges par loop chalata hai: while (!vif.monitor_cb.pready) measured_waits++;. Jitnay clock cycles tak PREADY zero rehta hai, woh exactly count hotay hain aur item mein tr.wait_cycles = measured_waits; store ho kar coverage ko sample hota hai.
Q6: Code Coverage aur Functional Coverage mein kya farq hota hai?
Jawab (Roman Urdu):
  • Code Coverage: Tool (VCS) automatically measure karta hai ke Verilog/SystemVerilog code ki kitni lines, branches, FSM states, aur toggles execute hui hain. Yeh batata hai: "Did I execute all the code?"
  • Functional Coverage: Verification Engineer design specification ke mutabiq covergroups define karta hai (e.g. address ranges, wait states, read/write cross). Yeh batata hai: "Did I verify all the required features and scenarios?"
Q7: Agar simulation ke dauran scoreboard error detect kare lekin test log mein `PASSED` print ho jaye, to is bug ko aap ne kaisay fix kiya?
Jawab (Roman Urdu): Yeh verification suites ka ek common bug hota hai jahan `TEST PASSED` ka UVM banner check condition se bahir likha hota hai. Hum ne tamam testcases mein banner ko strictly else block ke andar lock kiya: if (env.scoreboard.matches != expected || env.scoreboard.errors != 0) uvm_error(...) else uvm_info("PASSED", UVM_LOW). Ab agar aik bhi mismatch ya error aaye to PASSED banner hargiz print nahi ho sakta.
Q8: UVM mein Phase Objections (`raise_objection` / `drop_objection`) ka kya maqsad hai?
Jawab (Roman Urdu): UVM mein simulation tab tak chalti hai jab tak kam az kam ek component ne phase objection raise ki ho. Har test ke run_phase ke shuru mein hum phase.raise_objection(this) call kartay hain taake test stimulus execute ho sakay, aur jab test complete ho jaye to phase.drop_objection(this) call kartay hain taake simulation cleanly end ho jaye. Agar objection drop na ho to simulation hang (timeout) ho jayegi.
Q9: `axi2apb_constrained_random_test` mein transaction count runtime par kaisay change hoti hai?
Jawab (Roman Urdu): Test ke build_phase mein hum UVM PlusArgs mechanism use kartay hain: 
void'($value$plusargs("NUM_TRANS=%d", num_transactions));
Agar user simulation command mein +NUM_TRANS=50 de, to variable 50 par set ho jata hai; agar na de to default 20 transactions rehti hain. Yeh regression suite ko flexible banata hai.
Q10: Functional Coverage mein `ignore_bins` kyun lagaye gaye?
Jawab (Roman Urdu): AXI standard mein 4 response codes hotay hain (OKAY, EXOKAY, SLVERR, DECERR). Lekin hamare bridge RTL mein response code hamesha 2'b00 (OKAY) hardcoded hai (unsupported feature). Agar hum EXOKAY, SLVERR, aur DECERR ko coverpoint mein rakhtay to woh kabhi hit na hotay aur coverage hamesha 50% par stuck rehti. Is liye unhein ignore_bins declare kiya gaya taake coverage metric actual implemented hardware ko reflect kare aur 100% achieve ho.
